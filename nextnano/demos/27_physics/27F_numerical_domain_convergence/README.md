> **One question:** Could numerical-domain choices be creating or moving the higher states?

## Run it

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27F --preflight
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27F --physics --yes
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27F --analyze
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27F --record PASS --conclusion "..."
```

`--preflight` needs no license and runs anywhere. `--physics` refuses to start against a Free build, refuses without `--yes`, and refuses while a prerequisite is unmet. `--analyze` never launches a solver.

## Pass condition

Every state energy is reported against each numerical knob, and each state is labelled converged or not-converged under an explicit tolerance. A physical state must not depend strongly on the outer boundary; any state that moves with the padding, the outer barrier width or the boundary condition is recorded as a numerical artifact of the Dirichlet box, not as physics. PASS is reached when every state carries that label.

## The controlled change

One numerical knob per deck, against the shared Demo 23 baseline. The sub-demo owns several knobs because the question is about the numerical domain as a whole, but no single deck turns more than one of them - except the state-count deck, where raising the number of states written requires raising the number solved.

Fields this sub-demo may change: `active_spacing_nm`, `quantum_region_padding_nm`, `period_barrier_nm`, `boundary`, `num_electrons`, `num_holes`, `output_state_count`.
At most **3** per deck. Everything else is inherited verbatim from the Demo 23 baseline, and `framework/registry.resolve` raises rather than generating a deck that breaks either rule.

| Deck | Changed fields | Question |
|---|---|---|
| `mesh_fine_0p025nm` | `active_spacing_nm` | Is the 0.05 nm active mesh converged? |
| `mesh_coarse_0p100nm` | `active_spacing_nm` | How far does a coarser mesh move the states? (sets the convergence slope) |
| `padding_4nm` | `quantum_region_padding_nm` | Do the states depend on where the Dirichlet walls are placed? |
| `padding_8nm` | `quantum_region_padding_nm` | Same question, further out - a physical state must stop moving |
| `outer_barrier_28p2nm` | `period_barrier_nm` | Does a thicker outer barrier change the high states or the continuum onset? |
| `states_24` | `num_electrons`, `num_holes`, `output_state_count` | Does simply asking for more states create new levels below the ones we use? |
| `boundary_neumann` | `boundary` | Is any state an artifact of the Dirichlet wall rather than of the barriers? |

## Cost

**Basis:** Seven decks at roughly the Demo 23 production cost (10 min 20 s each), except the 0.025 nm mesh, which doubles the grid and therefore costs several times more. The 0.05 nm / 2 nm-padding / 18.2 nm-outer-barrier / Dirichlet control is NOT rerun: demo_results/demo23/raw/production_y_n301_k0100 is that exact case. Demo 23 also already holds 101 and 201 k-point grids, so k-grid convergence is reused rather than recomputed.

`outputs/COST_STATEMENT.md` is regenerated by preflight from the resolved configuration, so it reflects the decks that actually exist rather than this document.

## The question

A physical result must not depend strongly on an arbitrary outer boundary. If a
state moves when the Dirichlet walls move, it is a property of the box, not of
the quantum wells — and it must never be entered into Equation 2.

## One knob per deck

| Deck | Knob | Baseline |
|---|---|---|
| `mesh_fine_0p025nm` | active mesh 0.05 → 0.025 nm | is 0.05 converged? |
| `mesh_coarse_0p100nm` | active mesh 0.05 → 0.10 nm | sets the convergence slope |
| `padding_4nm` | quantum-region padding 2 → 4 nm | where are the Dirichlet walls? |
| `padding_8nm` | quantum-region padding 2 → 8 nm | further out — a physical state must stop moving |
| `outer_barrier_28p2nm` | outer barrier 18.2 → 28.2 nm | does the continuum onset move? |
| `states_24` | 14 → 24 states written (10 e, 14 h solved) | does asking for more create levels below the ones we use? |
| `boundary_neumann` | Dirichlet → Neumann outer boundary | is any state an artifact of the wall type? |

The state-count deck changes three fields because they are physically
inseparable — you cannot write more states than you solve. `config.yaml` sets
`max_fields_per_deck: 3` for exactly that reason, and the framework refuses a
deck that exceeds it.

## What is reused

The 0.05 nm / 2 nm / 18.2 nm / Dirichlet control is **not** rerun: it is
`demo_results/demo23/raw/production_y_n301_k0100`. Demo 23 also already holds 101-
and 201-point k grids (`grid_y_n101_k0100`, `grid_y_n201_k0100`), so k-grid
convergence is reused rather than recomputed — which is why no k-grid deck
appears above.

## The output that matters

`STATE_ARTIFACT_LABELS.csv`. Every state gets CONVERGED or NUMERICAL ARTIFACT
against an explicit tolerance, with the knob that moved it. That table is what
27K and 27C consume.

## Analysis artifacts

The analysis stage will write these into `outputs/`. Until the data exists they are listed as PENDING DATA in `outputs/ANALYSIS.md` and **no placeholder file is created**:

- `CONVERGENCE_TABLE.csv`
- `STATE_ARTIFACT_LABELS.csv`
- `BOUNDARY_SENSITIVITY.csv`
- `CONVERGENCE_VERDICT.md`

## Data harvest

Whenever this sub-demo's decks are solved, the shared broad harvest in `demo27_config.yaml` is requested — eigenenergies, envelopes, kp8 spinors, CB/HH/LH/SO character, probabilities, transition energies, dipole and momentum matrix elements, oscillator strengths, band edges, alloy composition, k vectors, dispersions and masses, plus electrostatic potential and strain where the deck already computes them.

No expensive new physics is enabled merely because an output would be interesting. The harvest costs disk, not solver time.
