```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27O --preflight
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27O --analyze
```

`--preflight` needs no license and runs anywhere. `--physics` refuses to start against a Free build, refuses without `--yes`, and refuses while a prerequisite is unmet. `--analyze` never launches a solver.

## Pass condition

The interband Bloch matrix element is derived from the k.p parameters rather than assumed, its dependence on band character, k and composition is reported, and the constant r_e,hh = 0.751 nm the chi2 engine currently uses is either confirmed within a stated tolerance or replaced with a justified k-dependent form. PASS requires the derivation and its uncertainty, not agreement.

## The controlled change

None inside nextnano. 27O changes the model of the microscopic dipole, not the structure or the solver settings.

This sub-demo changes no deck field.

## Cost

**Basis:** The kp8-derived route is hours of post-processing on 27B's harvest. The DFT route is day-scale and needs software this project does not have, which is why the range is this wide and why the sub-demo starts as a scoping exercise.

`outputs/COST_STATEMENT.md` is regenerated by preflight from the resolved configuration, so it reflects the decks that actually exist rather than this document.

## The approximation under test

The chi2 engine uses a constant interband Bloch matrix element,
`r_e,hh = 0.751 nm` (Demo 23's `chi2.r_e_hh_nm`). 27O asks whether that constant
is adequate, or whether `r_e,hh(k)` varies enough with band character, k or
composition to matter.

## Why it is last

A microscopic correction to the Bloch factor is only meaningful once the
envelope-function physics above it is understood. If 27D shows the geometry is
wrong, or 27G shows the cutoff convention is wrong, correcting the Bloch factor
first would be tuning a small term on top of a large error.

## Two routes, in order

**1. kp8-derived (no new software).** 27B's harvest contains the kp8 interband
momentum matrix elements at every k. `r_e,hh(k)` follows from those and the
transition energies. This is hours of post-processing and it should be attempted
first.

**2. Independent DFT / HSE06 (new software).** A first-principles calculation of
GaAs and Al0.55Ga0.45As to validate the k.p-derived value. This needs tooling
this project does not have, and provisioning it is a separate decision with its
own cost. `config.yaml` records it as `external_tooling.status: NOT PROVISIONED`
and Demo 27 does not assume it will happen.

## What passing means

The derivation and its uncertainty, not agreement. `r_e,hh` is either confirmed
within a stated tolerance or replaced with a justified k-dependent form. A result
that says "the constant is adequate to 3%" retires the question.

## Data harvest

Whenever this sub-demo's decks are solved, the shared broad harvest in `demo27_config.yaml` is requested — eigenenergies, envelopes, kp8 spinors, CB/HH/LH/SO character, probabilities, transition energies, dipole and momentum matrix elements, oscillator strengths, band edges, alloy composition, k vectors, dispersions and masses, plus electrostatic potential and strain where the deck already computes them.

No expensive new physics is enabled merely because an output would be interesting. The harvest costs disk, not solver time.
