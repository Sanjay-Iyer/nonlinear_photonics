```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27A --preflight
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27A --physics --yes
```

`--preflight` needs no license and runs anywhere. `--physics` refuses to start against a Free build, refuses without `--yes`, and refuses while a prerequisite is unmet. `--analyze` never launches a solver.

## Pass condition

Demo 25's PILOT_GATE.json records status PASS: more than one k point carries both energies and envelopes, and an identifiable k-vector file exists so each state can be tied to a k value. That is exactly enough to construct O_nm(k), z_e,nl(k) and z_hh,ml(k). Anything less is a FAIL and 27B stays blocked.

## Delegation

This sub-demo **does not implement its own calculation**. It runs `25_finite_k_matrix_element_validation`, one explicit command per stage, and records what it ran in `outputs/PROFESSIONAL_RUN_MANIFEST.json`.

| Stage | Command |
|---|---|
| preflight | `python 25_finite_k_matrix_element_validation/run_demo25.py --preflight` |
| physics | `python 25_finite_k_matrix_element_validation/run_demo25.py --pilot` |
| analyze | `python 25_finite_k_matrix_element_validation/run_demo25.py --pilot-audit` |

*Why:* Demo 25 was built for this exact question and has never been run. Its six variants isolate one candidate explanation each (k_integration, no_density, k_point_subdirectories, symmetry, dispersion coexistence, plus the Demo 23 control), so one work-laptop trip settles the syntax.

## The controlled change

Which per-k outputs nextnano++ is asked for, and whether the k-integration grid is enabled. Geometry, materials, mesh and temperature are Demo 23's, unchanged; Demo 25 enforces that with a structural diff against the Demo 23 deck.

This sub-demo changes no deck field.

## Cost

**Basis:** Demo 23 solved 301 dispersion k points for 14 states in 10 min 20 s on the work laptop. The pilot is 6 decks x 4 k points but with 32 states and full envelope output at every k, so it is dominated by output volume, not by the eigenvalue problem. Demo 25's own pilot_audit then measures seconds-per-k and bytes-per-k for real and sizes 27B from the measurement rather than from this estimate.

`outputs/COST_STATEMENT.md` is regenerated by preflight from the resolved configuration, so it reflects the decks that actually exist rather than this document.

## Why this is first

It is twenty minutes, and it decides which output keywords make nextnano++ write
state data at finite k. That answer applies to **every later Professional deck in
the campaign**, so running a three-hour sub-demo before it risks spending three
hours to collect a harvest that could have been better.

## Why Demo 23 only ever produced `k00000`

Demo 23's deck asked for `all_k_points = yes` on `output_states`,
`transition_energies`, `dipole_moment_matrix_elements` and
`momentum_matrix_elements`, and still wrote state and matrix files for `k00000`
only. The cause is in the same deck:

```
kp_8band{ ... k_integration_disabled{}
          dispersion{ path{ ... num_points = 301 } } }
```

`all_k_points` follows the **k-integration** grid, not the dispersion path. With
`k_integration_disabled{}` that grid holds exactly one point, so there was one
file set to write. `dispersion{ path{} }` is a separate mechanism that emits
energies, k vectors and masses only — which is exactly what Demo 23 did get.

That is the leading hypothesis, not a certainty, which is why the pilot tests it
against the alternatives instead of assuming it.

## The six variants

| Variant | Question it isolates |
|---|---|
| `A0_control_demo23_style` | Control — does the Demo 23 configuration still give only `k00000`? |
| `A1_kint_nodensity` | Does `k_integration{}` alone produce multi-k state output? |
| `A2_kint_density` | Does `no_density = yes` suppress the k-integration loop? |
| `A3_kint_subdirs` | Does per-k output need `k_point_subdirectories = yes`? |
| `A4_kint_symmetry_C4` | How does `symmetry` change the emitted k-point set? |
| `A5_kint_plus_dispersion` | Can `k_integration` and `dispersion{path{}}` coexist for cross-check? |

## The gate is filesystem-based

A zero exit status is **not** accepted as evidence. Demo 23 exited cleanly and
still wrote only `k00000`. Demo 25's `pilot_audit.py` counts the files that
actually exist per k point, and additionally requires an identifiable k-vector
file — finite-k data that cannot be tied to a k value is not usable, however many
files were written.

## What to produce

Demo 25 writes `outputs/PILOT_FINITE_K_OUTPUT_AUDIT.md`, which classifies every
requested quantity — energies, finite-k envelopes, full kp8 spinors, CB/HH/LH/SO
fractions, optical momentum elements, dipole/position elements, oscillator
strengths, polarization-resolved strengths, localization, raw eigenvectors — as
AVAILABLE, NOT AVAILABLE, AVAILABLE BUT UNPARSED, or REQUIRES A DIFFERENT
NEXTNANO OPTION.

## If it fails

**Stop. Do not proceed to 27B.** Read `outputs/PILOT_BLOCKER_REPORT.md` in Demo
25. There is no code path in which Demo 25 or Demo 27 substitutes M(k) = M(0) and
calls the result a finite-k validation.

## Analysis artifacts

The analysis stage will write these into `outputs/`. Until the data exists they are listed as PENDING DATA in `outputs/ANALYSIS.md` and **no placeholder file is created**:

- `PILOT_OUTPUT_AUDIT.md`

## Data harvest

Whenever this sub-demo's decks are solved, the shared broad harvest in `demo27_config.yaml` is requested — eigenenergies, envelopes, kp8 spinors, CB/HH/LH/SO character, probabilities, transition energies, dipole and momentum matrix elements, oscillator strengths, band edges, alloy composition, k vectors, dispersions and masses, plus electrostatic potential and strain where the deck already computes them.

No expensive new physics is enabled merely because an output would be interesting. The harvest costs disk, not solver time.
