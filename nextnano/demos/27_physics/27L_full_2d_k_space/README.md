# Demo 27L — Full 2D in-plane (kx, ky) validation

> **One question:** Does full 2D in-plane physics materially change chi2 compared with radial integration?

## Run it

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27L --preflight
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27L --physics --yes
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27L --analyze
```

```bash
python nextnano/demos/27_physics/run_demo27.py --demo 27L --record PASS --conclusion "..."
```

`--preflight` needs no license and runs anywhere. `--physics` refuses to start against a Free build, refuses without `--yes`, and refuses while a prerequisite is unmet. `--analyze` never launches a solver.

## Pass condition

chi2 is computed by genuine 2D integration over the in-plane zone and compared directly against the radial model on the same structure and the same cutoff. PASS means the difference is quantified. A difference below the 27H tolerance is a successful result that validates every radial calculation this project has done.

## Evidence gate

This sub-demo runs **only if**: 27H reports directional anisotropy above its stated tolerance. If it does not, this sub-demo must be recorded NOT NEEDED. It is the most expensive calculation in the campaign and there is no reason to spend it on a question 27H can close for a fifth of the cost.

If the condition fails, record it as `NOT NEEDED`. That satisfies any downstream prerequisite, so closing the question this way strands nothing.

## The controlled change

The k sampling changes from a 1D radial path to the 2D k-integration grid. The point count changes with it because 61 points along a path and 61 points across a 2D grid are not the same object; the cutoff, the structure and the state count are the Demo 23 baseline.

Fields this sub-demo may change: `k_mode`, `k_points`, `symmetry`.
At most **3** per deck. Everything else is inherited verbatim from the Demo 23 baseline, and `framework/registry.resolve` raises rather than generating a deck that breaks either rule.

| Deck | Changed fields | Question |
|---|---|---|
| `k2d_integration_n61` | `k_mode`, `k_points` | Does the 2D in-plane integral differ from the radial one? |

## Cost

**Basis:** k_integration builds a two-dimensional in-plane grid, so num_points = 61 with symmetry = none is of order 61^2 = 3700 k-point solves against the 301 of a dispersion path - roughly twelve times the Demo 23 production run before the per-k output volume is counted. This is a planning estimate with wide bounds and it should be re-derived from the 27A pilot's measured seconds-per-k and bytes-per-k before the run is launched.

`outputs/COST_STATEMENT.md` is regenerated by preflight from the resolved configuration, so it reflects the decks that actually exist rather than this document.

## Do not run it speculatively

It runs **only** if 27H reports directional anisotropy above its stated
tolerance. If 27H finds the in-plane response isotropic, record this as
`NOT NEEDED`. That is not a shortcut: an isotropic 2D integral and a radial
integral are the same integral, and computing it the expensive way to confirm
that is not evidence, it is arithmetic.

## Re-derive the estimate before launching

The runtime and volume bounds in `config.yaml` are wide because they are a
planning estimate from geometry, not a measurement. The 27A pilot measures
seconds-per-k and bytes-per-k for real. **Re-derive this sub-demo's cost from
those numbers before spending a day on it**, and update `config.yaml` if the
measurement disagrees.

## What it must produce

A direct comparison of chi2 computed by genuine 2D integration against the radial
model, **on the same structure and the same cutoff**, so the difference is
attributable to the integration and to nothing else. A difference below the 27H
tolerance is a successful result that validates every radial calculation this
project has done.

## Prerequisites

Both 27A and 27H. 27A because 2D k-space state output is the same output
capability the pilot establishes; 27H because it is the reason to exist.

## Data harvest

Whenever this sub-demo's decks are solved, the shared broad harvest in `demo27_config.yaml` is requested — eigenenergies, envelopes, kp8 spinors, CB/HH/LH/SO character, probabilities, transition energies, dipole and momentum matrix elements, oscillator strengths, band edges, alloy composition, k vectors, dispersions and masses, plus electrostatic potential and strain where the deck already computes them.

No expensive new physics is enabled merely because an output would be interesting. The harvest costs disk, not solver time.
